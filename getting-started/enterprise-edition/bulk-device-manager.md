# Device Telemetry

The **Bulk Device Manager** is the fleet-wide collector. While [QoE Analysis](qoe-analysis.md) explains _what_ Oktopus does with the data, this page configures _how and when_ that data is pulled from every CPE in the organization.

It is reached from **Settings → Bulk Device Management**, and it drives two independent pipelines:

| Pipeline            | What it does                                                                                                                                                            | Cost profile                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Data Collection** | Pulls telemetry from every device — Wi-Fi, hardware, PON/xDSL, interfaces, connected devices, ping results, site survey — and stores one document per device per cycle. | Kilobytes per device. Cheap, runs often.                                        |
| **Speed Test**      | Runs download and/or upload throughput tests against your HTTP servers.                                                                                                 | Tens to hundreds of megabytes **per device, per test**. Expensive, runs rarely. |

> **Important:** The two pipelines have **separate schedules, separate parallelism caps and separate enable switches**. Turning off Data Collection does not turn off Speed Test, and vice-versa. This separation exists precisely because their bandwidth cost differs by three orders of magnitude.

## How a cycle works

1. **The scheduler wakes up.** Every tenant has its own schedule. When the configured **Interval** has elapsed since the last cycle started, a new cycle opens.
2. **One job per device.** The cycle publishes one job per device in the fleet — including devices that are currently offline. Offline devices are skipped when their job is picked up; they are not retried inside the same cycle.
3. **Workers drain the queue.** Workers pull jobs and talk to the CPEs. At most **Max Devices in Parallel** devices are in flight at any moment for your organization. Each tenant gets its own queue, so a large fleet in one organization cannot starve a small one in another.
4. **Documents are stored, the cycle closes.** Each device that was reachable produces one stored document. When every job has been acknowledged (or the cycle times out), the cycle closes and its duration and success count become the **Last Cycle** figure shown on screen.

Requests generated by these pipelines run at the **lowest priority** in the device message queue. A technician opening a device screen, a Script or a Service always preempts bulk traffic on the same CPE.

## Global Settings

### Timezone

The IANA timezone (for example `America/Sao_Paulo`, `Europe/London`) used to interpret the **Critical Period** below.

This is a **global** setting: it applies to both pipelines and to every device model. It is deliberately not overridable per model — a fleet lives in one operational timezone.

> **Note:** Use a real IANA zone, not a fixed UTC offset. `Europe/London` follows BST automatically; `UTC+1` would not.

## Data Collection Pipeline

### Enabled

Master switch for telemetry collection. When off, no collection cycles are scheduled for the organization and all the fields below are hidden.

Leaving it unset on a brand-new organization is equivalent to **enabled** — collection is the historical default behaviour.

### Critical Period — Start / End

A daily maintenance window, expressed in the **Timezone** above, during which the **intrusive** part of the collection is allowed to run: the **Wi-Fi Site Survey**.

A site survey forces the CPE's radio to scan the spectrum, which briefly disturbs the customer's Wi-Fi. Every other stage of collection (hardware, interfaces, connected devices, PON, ping…) runs on every cycle regardless of this window — only the site survey is gated by it.

* The window is evaluated on hour and minute only, in the tenant's timezone.
* A window that crosses midnight is supported: `23:00 → 04:00` means 23:00 to 03:59 the next day.
* A zero-length window (start equal to end) means **no usable window is configured**, and the site survey never runs.

**Example**

| Timezone            | Start   | End     | Effect                                                                    |
| ------------------- | ------- | ------- | ------------------------------------------------------------------------- |
| `America/Sao_Paulo` | `01:00` | `05:00` | Site survey only between 1 AM and 5 AM local Brazilian time.              |
| `Europe/London`     | `01:30` | `02:45` | Follows GMT/BST automatically — the window stays at 01:30 local all year. |
| any                 | `00:00` | `00:00` | Site survey disabled.                                                     |

### Ping Test

#### Enable Ping Test

When on, each collection cycle also asks the CPE to ping the servers listed below, and stores the result (success/failure counts, min/avg/max RTT) inside the same telemetry document. These results feed the **Ping** component of the QoE health score.

#### Ping Servers

The list of hosts to ping. Add entries with the **+** button, remove them with the bin icon.

Accepts hostnames or IP addresses:

```
8.8.8.8
1.1.1.1
gateway.myisp.net
```

Each server adds roughly **160 bytes** to every stored document, per device, per cycle. On a 60,000-device fleet collecting every 35 minutes, one extra ping server costs about **400 MB/day**. The **Collection Volume Estimate** below reacts live as you add or remove entries.

> **Important:** If **Enable Ping Test** is on, the server list cannot be empty — the configuration is rejected on save.

### Interval (minutes)

How long after a cycle starts before the next one is allowed to start.

* **Minimum: 35 minutes.** Values below this are rejected on save.
* Typical values: `35` for near-real-time dashboards, `60`–`240` for large fleets where bandwidth matters more than freshness.

The interval controls **how many cycles run per day**, never how much a single cycle carries. Doubling the interval halves the daily volume; it does not change **Volume per Cycle**.

> **Note:** If a cycle takes longer than the interval to drain, the next cycle simply starts as soon as the previous one closes. The interval is a floor, not a guarantee.

### Max Devices in Parallel

The fleet-wide cap on how many devices your organization talks to at the same time during a collection cycle.

* The helper text shows the **deployment ceiling** when one is configured .Typing a higher number clamps it to the ceiling.
* Your value is enforced per tenant: with `100`, exactly 100 device jobs are in flight for your organization at any instant, independent of what other organizations are doing.

**How to choose it**

| Fleet size     | Interval   | Reasonable starting point       |
| -------------- | ---------- | ------------------------------- |
| < 5,000        | 35 min     | 50                              |
| 5,000 – 50,000 | 35–60 min  | 100                             |
| > 50,000       | 60–240 min | 200–500, subject to the ceiling |

Raising this number shortens the cycle but increases simultaneous load on the ACS and on your access network. Watch **Collection Cycle Time** and **Implied Bandwidth** below while you adjust it.

### Collection Volume Estimate

A live projection that recalculates as you type. The header line reads:

> Based on **N** devices and \~**X** KB per device per cycle (collection + ping).

* **N** is the **total** number of devices in the organization — the same total the overview status chart adds up, not just the ones online right now. A cycle dispatches a job per device, and offline devices come back.
* **X** is the measured average size of a stored telemetry document over the last 24 hours, when there is history. On a fresh fleet it falls back to a conservative 25 KB + 160 bytes per ping server.

Hover any figure for its explanation:

| Figure                    | Meaning                                                                                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Volume per Cycle**      | Total data expected to cross the platform in one full cycle, covering every device. Independent of the interval.                                                                                                   |
| **Volume per Day**        | Cycle volume multiplied by how many cycles fit in 24 hours at the configured interval.                                                                                                                             |
| **Volume per Month**      | Daily volume × 30.                                                                                                                                                                                                 |
| **Collection Cycle Time** | Estimated time to cover the whole fleet: devices ÷ parallel slots × the typical time per device. Uses the real duration of the last finished cycle when one exists.                                                |
| **Implied Bandwidth**     | Average bandwidth while the cycle runs: cycle volume ÷ cycle time.                                                                                                                                                 |
| **Last Collection Cycle** | The last finished cycle, shown as `duration · devices`. Example: `2m · 2991` means the cycle took 2 minutes and 2,991 devices were online and actually produced data. Offline devices are skipped and not counted. |

> **Note:** Estimates are projections, not billing figures. The real number moves with how many devices are offline at cycle time; Oktopus continuously re-anchors the estimate on the measured output of the last 24 hours.

## Speed Test Pipeline

> Download/upload tests run on their own schedule, independent from data collection.

### Enabled

Master switch for the whole speed-test pipeline. Turning it on enables both the download and the upload test; the two individual switches below let you keep only one.

Turning it off stops all scheduled speed tests. It does **not** affect the on-demand speed test a technician runs from an individual device page.

### Enable Download Speed Test

Runs an HTTP download from the **Download Server** flagged as default. The volume moved per device equals the size of the file being served.

### Enable Upload Speed Test

Runs an HTTP upload to the **Upload Server** flagged as default, using the size selected in the **Upload File Sizes** catalogue.

### Download Servers

The list of HTTP endpoints devices download from during a scheduled test.

| Field          | Meaning                                                                                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Server URL** | Full URL of the file the CPE downloads.                                                                                                                         |
| **Default**    | Exactly one entry is the default — the one the bulk pipeline uses on every scheduled cycle. The others remain available for on-demand tests from a device page. |

```
http://speedtest.myisp.net/files/100MB.bin
http://speedtest-sp.myisp.net/files/50MB.bin
```

> **Note:** Name the file with its size (`100MB`, `1GB`). The estimate card reads the size out of the URL to project the download volume. A URL with no size in its name contributes 0 to the download half of the estimate.

If **Enable Download Speed Test** is on, this list cannot be empty.

### Upload Servers

Same shape as the download list: **Server URL** plus a **Default** flag. This is where the CPE `PUT`s / `POST`s the generated payload.

```
http://speedtest.myisp.net/upload
```

If **Enable Upload Speed Test** is on, this list cannot be empty.

### Upload File Sizes

A catalogue of upload payload sizes, edited the same way as on the Device Management screen.

| Field         | Meaning                                                                                              |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| **Size (MB)** | The payload size, in megabytes. Stored internally in bytes.                                          |
| **Default**   | The size the bulk pipeline sends on every scheduled upload test. Exactly one entry carries the flag. |
| **+** / bin   | Add or remove an entry.                                                                              |

The entries you define here are also the options a technician sees on a device's diagnostic screen, so the catalogue is the single source of truth for upload sizes across the platform.

**Defaults**

* When an organization has never configured a catalogue, a single **50 MB** entry is created and flagged default.
* Removing the entry that carried the flag promotes the first remaining entry to default.

### Speed Test Interval (minutes)

How often the speed-test cycle restarts, independent from the collection interval.

* **Minimum: 35 minutes**, enforced on save.
* **Default: 60 minutes** when the organization never chose one.
* On large fleets, values of several hours are common — a single cycle can move terabytes.

### Max Devices Testing in Parallel

The fleet-wide cap on simultaneous speed tests.

* **Default: 100** when the organization never chose one.

This is the single most important field for protecting your network. **Implied Bandwidth** below turns it into a concrete number: it is the peak simultaneous traffic the tests will generate.

> **Warning:** 100 devices testing in parallel at a typical 100 Mbps each is **10 Gbps** of simultaneous traffic through your speed-test servers and transit. Size this against the capacity you are willing to spend, not against how fast you want the cycle to finish.

### Speed Test Volume Estimate

Same layout as the collection estimate. The header line reads:

> Based on **N** devices and \~**X** MB per test (download + upload).

where **X** is the default download file size plus the default upload size, counting only the halves that are enabled.

| Figure                    | Meaning                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Volume per Cycle**      | Devices × (download size + upload size).                                                                         |
| **Volume per Day**        | Cycle volume × cycles per day at the configured interval.                                                        |
| **Volume per Month**      | Daily volume × 30.                                                                                               |
| **Speed Test Cycle Time** | Devices ÷ parallel slots × the measured median duration of one test (30 s assumed until there are real samples). |
| **Implied Bandwidth**     | Parallel devices × the measured median throughput per test. This is the peak, not an average.                    |
| **Last Speed Test Cycle** | `duration · devices`, same reading as the collection figure.                                                     |

**Worked example**

A 60,000-device fleet, download 100 MB + upload 50 MB, 100 devices in parallel, 60-minute interval, measured median 30 s and 100 Mbps per test:

* Volume per Cycle = 60,000 × 150 MB ≈ **8.6 TB**
* Cycle Time = 60,000 ÷ 100 × 30 s = **5 h** — longer than the interval, so cycles run back to back
* Volume per Day = 8.6 TB × (24 h ÷ 5 h) ≈ **41 TB**
* Implied Bandwidth = 100 × 100 Mbps = **10 Gbps**

Dropping the upload test and moving to 25 devices in parallel takes this to ≈5.7 TB per cycle and 2.5 Gbps, at the cost of a 20-hour cycle.

## Device Model Specific Configurations

Everything above is the organization-wide baseline. This section lets you override it for individual device models — useful when one model has a fragile radio, cannot sustain a large upload, or should be excluded from a pipeline entirely.

Use **Add Device Model** to pick a model from the ones present in your fleet. Each model expands into two cards mirroring the global ones.

**What you can override per model**

| Data Collection Pipeline | Speed Test Pipeline          |
| ------------------------ | ---------------------------- |
| Enabled                  | Enabled                      |
| Enable Ping Test         | Enable Download Speed Test   |
| Ping Servers             | Enable Upload Speed Test     |
|                          | Download Servers (+ Default) |
|                          | Upload Servers (+ Default)   |

**What is deliberately global and never appears per model**

Timezone, Critical Period, Interval, Max Devices in Parallel, Speed Test Interval, Max Devices Testing in Parallel, and the Upload File Sizes catalogue.

These are scheduling and capacity decisions that apply to one shared queue per organization. Letting a single model define its own interval or its own parallelism would make the fleet-wide caps meaningless, so the platform inherits them from the global configuration instead.

**Example**

| Goal                                              | Configuration                                                                                                           |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| A legacy model whose radio crashes on site survey | Add the model, leave **Data Collection → Enabled** on, and turn off its ping test if it also misreports RTT.            |
| A 4G CPE on a metered link                        | Add the model and turn **Speed Test Pipeline → Enabled** off. Telemetry keeps flowing; no throughput test is scheduled. |
| A model that only reaches a regional server       | Add the model and give its Speed Test card its own Download/Upload server list.                                         |

***

## Saving

* **Save** applies the configuration. It stays disabled while any required field is empty or invalid — in practice, a parallelism field left blank or a speed-test interval below 35 minutes.
* A confirmation dialog appears before the change is applied, because it affects how device data is fetched across the whole organization.
